# Verification

## Verification Protocol (Strict)

### Negative Premise

- AI는 사용자 요청에 "Yes"로 답하려는 성향이 강함. 질문 단계에서부터 실패 가능성을 열어둔다
- 해결책 제안 전 현재 버전에서 deprecated 여부 교차 확인. 불확실하면 "Unverified"로 표기
- 기능이 삭제된 버전이나 특정 OS에서 미지원하는 경우가 있는지 먼저 확인한다
- 공식 릴리즈 노트(Changelog)나 공식 문서에 명시된 경로만 안내. 추측 금지

### Ground Truth

- UI 메뉴는 환각(Hallucination)이 가장 심한 영역. 시스템 레벨 검증을 우선한다
- 설정 파일(Config/Plist/JSON)의 키/필드명으로 확인. 해당 키가 없으면 환각일 확률 99%
- OS별(Windows/macOS/Linux) UI 및 기능 제약을 먼저 구분하여 안내한다
- URL 제공 전 항상 404 확인. 환경 허용 시 `curl`, `ls`, `cat`으로 파일 경로 검증
- 커뮤니티(Reddit, StackOverflow)나 공식 이슈 트래커에서 관련 키워드 검색 후 요약

### 3-Strike Rule

- 제안한 해결책이 2회 실패하면 동일 로직 반복 금지. 즉시 중단
- Strike 1: 안내한 경로에 기능 없음 → "없다"고 명시 후 재탐색
- Strike 2: 설정 파일 수정 후 반응 없음 → 버전/OS 제약 확인
- Strike 3: 동일 논리 반복 → 대화 중단. 공식 문서 또는 이슈 트래커를 직접 검색해 재검증

### Goal-Driven Execution (Karpathy)

- 작업을 검증 가능한 목표로 변환:
  - "fix bug" → "버그 재현 테스트 작성 → 통과 → 회귀 없음 확인"
  - "refactor X" → "리팩토링 전후 테스트 통과 확인"
  - "add validation" → "유효하지 않은 입력에 대한 테스트 작성 → 통과"
- 다단계 작업은 각 단계에 verify 체크포인트 명시:
  ```
  1. [Step] → verify: [check]
  2. [Step] → verify: [check]
  ```

**안티패턴: 모호한 접근**
```
# ❌ "인증 시스템 고쳐줘" → "코드 리뷰→이슈 식별→개선→테스트" (성공 기준 없음)
# ✅ 성공 기준 정의: "비번 변경 후 기존 세션 무효화되는가?"
#   1. 재현 테스트 작성 → verify: 테스트 실패 (버그 확인)
#   2. 세션 무효화 구현 → verify: 테스트 통과
#   3. 기존 인증 테스트 → verify: 회귀 없음
```

**안티패턴: 재현 없이 수정**
```
# ❌ "정렬이 중복 점수에서 깨짐" → 바로 sort 로직 변경
# ✅ 먼저 중복 점수 케이스 테스트 작성 → 실패 확인 → 수정 → 테스트 통과 확인
```

### Response Guidelines

- 버전/시점에 따라 결과가 달라지는 기술 응답은 확인 기준일과 대상 버전을 명시
- 스크린샷 격리: 새 스크린샷 업로드 시 이전 이미지는 만료. 현재 첨부 이미지만 Ground Truth로 사용
- 최신 버전 기준: 소프트웨어/하드웨어 정보는 항상 현재 최신 버전으로 안내

## Problem Solving Process

0. 가정 명시: 구현 전 가정을 나열. 불확실하면 사용자에게 확인
    - 여러 해석이 가능하면 모두 제시 (3-Options 활용)
    - 더 간단한 방법이 있으면 먼저 제안
    - 이해 안 되면 멈추고 질문

   **안티패턴: 숨겨진 가정**
    ```
    # ❌ "유저 데이터 내보내기" → 전체 유저, JSON/CSV, 파일 위치, 필드 모두 가정하고 구현
    # ✅ 먼저 확인: 범위(전체/필터링)? 포맷(브라우저 다운/API/백그라운드)? 필드(민감정보)? 볼륨?
    ```

   **안티패턴: 여러 해석을 조용히 선택**
    ```
    # ❌ "검색 빠르게 해줘" → 캐시+인덱스+비동기 200줄 추가 (latency인지 throughput인지 확인 없이)
    # ✅ 제안: 1) 응답시간 단축(인덱스) 2) 동시처리 향상(async) 3) 체감속도(점진 로딩) — 어떤 게 필요?
    ```
1. 분석: 파일 구조와 관련 코드를 먼저 읽고 분석
2. 원인: 문제의 근본 원인을 논리적으로 추론
3. 계획: 단계별 해결책 제시
4. TDD: 계획 수립에 맞게 테스트 코드 작성
5. 실행: 개발 시작
6. 검증: 변경 범위에 맞는 프로젝트의 test/lint/typecheck/build 명령으로 검증
7. 복구: 심각한 오류가 있을 때만 사용자의 동의 후 되돌림
